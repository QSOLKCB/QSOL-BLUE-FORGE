# CI supervision and the v1 conformance floor

The constitutional identity remains `blue-forge.core-invariants/v1`.
These controls implement BF-INV-003, BF-INV-004, BF-INV-006, BF-INV-009,
BF-INV-010, BF-INV-013 and BF-INV-014 without changing receipt semantics.

## Trust boundaries

Frozen tests, their inputs, and their expected results belong to the trusted
oracle. Only the implementation under test comes from proposed HEAD in the
frozen/proposed workspace. All frozen fixtures and schemas are materialized
from `BLUE_FORGE_TRUSTED_REF`. The v1 case fixture, schemas, supervisor and
isolated launcher also have exact Git mode/type/blob checks against that ref.

The supervisor executes assertions in a trusted worker interpreter. Proposed
`blue_forge` imports and API calls run in a different process under the distinct
`blueforge-rpc` UID. Hiding Python globals, private classes or signing keys inside
an interpreter which imports proposed code is not an isolation mechanism.

Actor responses are untrusted data. The trusted worker compares that data with
frozen assertions and literal conformance vectors. Completion is HMAC-authenticated
outside the proposed interpreter; the actor never receives the completion key.
A MAC generated by proposed code is never accepted as test completion. These are
regression checks, not cryptographic attestation that arbitrary source is honest.

## Preserving the tested operation

The bridge forwards package and submodule access, including `blue_forge.core`,
`blue_forge._validation_patch` and `blue_forge.schema_vocabulary`. Objects stay
alive in the actor between operations. Factories, attributes, copies, dataclass
replacement and low-level result mutation therefore exercise actual proposed
objects, not a reimplementation in the proxy.

A bounded graph representation preserves primitive types and shared references.
Trusted test subclasses are reconstructed from their frozen class definitions;
base-container descriptors copy their stored contents without calling overridden
iterators, `items()` or `__len__`. The proposed validation boundary consequently
receives the subclass it was intended to reject. Unsupported transport operations
fail explicitly; they do not silently normalize input or count as successful
verification.

The complete proposed test suite is also run through the same bridge before the
ordinary repository suite. This detects missing proxy coverage before a future
baseline promotion. It does not make PR-added tests authoritative or replace the
separate frozen/proposed stage.

## Kernel isolation and cleanup

`scripts/run_proposed_isolated.py` is installed root-owned from the external
baseline. Its narrow elevated role is to construct and destroy isolation, not to
execute proposed Python as root. The actor runs only after dropping UID, groups
and capabilities and setting `no_new_privs`, inside fresh mount, PID and network
namespaces, with a private HOME and explicit address-space, CPU, process-count,
file-size and descriptor limits.

The actor is PID 1 in its namespace. Its termination destroys its descendants,
including children launched through native subprocess paths and `setsid()`.
A private FIFO owned by the trusted worker controls the root launcher's lifetime.
Worker completion, timeout or unexpected death closes that FIFO; the launcher
then tears down the namespace before reporting completion. The actor cannot keep
the FIFO alive because it does not inherit the descriptor and cannot access its
private directory. Parent-death signals and a hard actor lifetime are additional
cleanup controls. Self-tests exercise detached children on success and forced
worker termination, as well as assertion, builtin and JSONEncoder tampering.

No signing secret or production credential is sent to proposed code. The archive
is never copied into these workspaces. The current-suite workspace is created
only after frozen supervision and remains root-owned/read-only; its runner and
HOME are distinct from the frozen runner and actor.

## Independent golden values

`tests/test_v1_golden_receipts.py` pins literal fixture, case, hardening-receipt
and regression-record SHA-256 values. The starting fixture is trusted Git blob
`822946019d01f8b1f5df91ebc3de7892e644a06e` (4321 bytes). The expected values were
computed from the documented material with independent hashlib and OpenSSL
SHA-256 calculations, not by asking the proposed `digest()` or evaluator for
expected output. The initial golden test was verified in CI before its addition
to the trusted floor. A changed algorithm or different hashed material therefore
cannot pass merely by agreeing with itself.

## Governance and local checks

Changes to the trusted supervisor, launcher or workflow require an explicit,
path-limited update to the external baseline. Adding golden tests does not advance
the reference implementation, existing frozen tests, schema bytes, fixture bytes
or immutable `v1.0.0` release. Semantic changes still require a new contract identity
and migration evidence.

Production supervision requires the isolated launcher and fails if it is missing.
`--local-test` is only a developer transport diagnostic for environments without
namespace privileges. It prints `LOCAL_TEST_ONLY`, never CI `PASS`, and must not
be used as evidence of kernel isolation or to authorize a CI run.
